# Frontend comparison: `dlib-bin` wheel vs. the legacy oracle

This report is the PR-4 evidence that the Python frontend
(`src/age_and_gender/_faces.py`, backed by the `dlib-bin` wheel) reproduces the
detector, five-point landmarks, and both individually extracted chips of the
PR-1 legacy oracle. It is generated by running the test suite below, not by
hand; regenerate it (update the numbers here) whenever the pinned `dlib-bin`
version changes.

## What was compared

`tests/parity/test_frontend.py` runs `age_and_gender._faces.FaceFrontend`
(the installed package's `dlib` frontend) against every fixture in
`tests/fixtures/legacy/*.golden.json` — the same frozen oracle output PR-1 and
PR-3 use for the neural-network side of parity. For each of the 4 documents:

| Document | Box mode | Faces | Notes |
| --- | --- | ---: | --- |
| `test-image.golden.json` | detect | 5 | Auto-detection, zero upsampling |
| `test-image-2.golden.json` | detect | 2 | Auto-detection, zero upsampling |
| `dogs.golden.json` | detect | 0 | No-face image |
| `explicit-boxes.golden.json` | explicit | 4 | Reversed order, a duplicate box, and one out-of-frame box |

11 faces total. For every one, the test asserts **exact** equality (not a
tolerance) of:

- The detected or explicitly-supplied rectangle, `[left, top, right, bottom]`.
- All five landmark points, `[x, y]`.
- Both the 32x32 gender chip and the 64x64 age chip, uint8 array equality.

It also re-derives the detector's own rectangles independently (`test_detection_
is_zero_upsampled_and_keeps_detector_order`) and confirms the explicit-box case
bypasses detection while preserving order, the duplicate box, and the
out-of-frame one (`test_explicit_boxes_bypass_detection_and_keep_order_and_
duplicates`).

## Result

All 11 faces across all 4 documents matched exactly: every rectangle, every
landmark point, and every one of the 22 chips (11 faces x 2 sizes). Zero
mismatches.

## Padding precision

`get_face_chip_details(shape, size, padding)` in this `dlib-bin` build accepts
`padding` at full C++ `double` precision — confirmed by passing the raw Python
float `0.2` and a `float32`-truncated `0.2` and observing different resulting
`chip_details.rect` coordinates at the 8th decimal digit. This matches the
vendored dlib 19.20 C++ signature (`interpolation.h`), `const double padding =
0.2`, which is what the legacy oracle actually calls. Both
`get_face_chip_details(...)` + `extract_image_chip(...)` and the `get_face_chip`
convenience wrapper reproduced the frozen chip bytes exactly on this corpus;
the production code uses the former, per spec/PR-4.md's preference for the
route that matches the double-precision padding path.

## Known batching trap, reproduced

`tests/parity/test_frontend.py::BatchingTrapRegressionTests` reruns the
batched-vs-individual comparison spec/PR-4.md documents from the investigation.
Batching `test-image.jpg`'s five 32x32 gender chips with `dlib.get_face_chips`
still disagrees with individually extracting each one via
`extract_image_chip`, changing exactly:

```text
[1540, 1665, 1796, 0, 1599]  # differing channel values per chip, out of 3072
```

This is the same counterexample recorded in `spec/INVESTIGATION.md`, confirming
it is not an artifact of the specific dlib version investigated: the currently
pinned `dlib-bin==20.0.1` wheel still shares a crop/pyramid across a batch. The
production frontend (`FaceFrontend.extract`) extracts each chip individually
and matches the golden (individually extracted) chips, not the batched ones.

## Environment this report was measured on

```text
dlib-bin        20.0.1
Pillow          12.3.0
Python          3.13.15
Platform        Linux-6.8.0-138-generic-x86_64-with-glibc2.35
```

`dlib-bin==20.0.1` was the newest version available on PyPI at investigation
time (`pip index versions dlib-bin` lists `20.0.1, 20.0.0, 19.24.6`, with
`20.0.1` marked `LATEST`); older releases were not evaluated. It is pinned
exactly in `pyproject.toml` rather than given a range, because this comparison
is what the pin certifies, and only `20.0.1` is what was actually compared.
Widening the pin (to a newer release once one ships, or to an older one) requires
rerunning this comparison against the candidate version and updating this
report; per spec/PR-4.md's stop condition, a version that changes any
rectangle, landmark, or chip is not a silent drop-in even if it installs
cleanly.

## Carried scope limit

This corpus is the same 4-document, 11-face set PR-1 froze — it covers
auto-detection, explicit boxes (reversed order, a duplicate, one out-of-frame),
and a no-face image, but not the 30-image/100-face corpus `spec/PR-1.md` and
`spec/INVESTIGATION.md` describe as deferred evaluation evidence.
`tools/legacy/README.md`'s "Current fixture scope" section already explains why
that corpus is not assembled from the vendored `tools/vendor/dlib/examples/faces/`
photographs: their redistribution rights are unclear, and README screenshots or
replacement-runtime output must not be promoted into goldens. Widening the
corpus with independently licensed images stays release-hardening work (PR-7),
not something this report works around by reusing unvetted assets.

## Reproduce

```bash
venv/bin/python -m pytest tests/parity/test_frontend.py -v
```
